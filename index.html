When a producer and a consumer
share memory, you get a race.

The bounded-buffer problem looks simple: one thread puts items in, another takes them out, and a shared count tracks how full the buffer is. But count++ and count-- aren't single steps, so the result depends on exactly when the CPU switches threads. Step through it, try every interleaving, and watch a real buffer break.

00 · Setup

The bounded buffer, unsynchronized

This is the textbook version (Silberschatz, Operating System Concepts). Both loops are correct when you read each one alone. The bug only shows up when they run at the same time, because both write to count.

Producer
while (true) {
    /* produce an item in next_produced */
    while (count == BUFFER_SIZE)
        ; /* do nothing: buffer full */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
    count++;
}
Consumer
while (true) {
    while (count == 0)
        ; /* do nothing: buffer empty */
    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
    count--;
    /* consume the item in next_consumed */
}
The hidden problem: the CPU doesn't execute count++ in one step. It compiles to load → modify → store. If the scheduler preempts a thread between its load and its store, the other thread's update gets overwritten. The next section shows this one instruction at a time.

      02 · Every possible schedule

      The scheduler has 20 choices. Only 2 of them are correct.

      With 3 producer instructions and 3 consumer instructions there are C(6,3) = 20 ways to interleave them. Each card below is one schedule, read left to right. Whichever thread stores last wins, and the other thread's update is lost. Click a card to replay it above.

      Final value of count across all 20 schedules

      Why only 2? The result is correct only when one thread's whole load-modify-store finishes before the other thread's load. That happens in exactly two schedules: PPPCCC and CCCPPP. In every other schedule the two threads overlap, and one update is lost.

      This is a race condition: the outcome depends on the relative timing of threads that access shared data, and at least one of them writes to it. The fix is to make those three instructions a critical section that only one thread can be inside at a time.

      04 · The solution

      Semaphores: count with the OS, not with a plain integer

      The classic fix uses three semaphores. empty counts free slots, full counts filled slots, and the binary semaphore mutex ensures only one thread touches the buffer and the in/out indices at a time. Each wait() and signal() is atomic, so no update can be lost. A thread that would overflow or underflow the buffer blocks instead of spinning.

      Producer
      semaphore mutex = 1, empty = N, full = 0;

while (true) {
    /* produce next_produced */
    wait(empty);   // block if no free slot
    wait(mutex);   // enter critical section
    buffer[in] = next_produced;
    in = (in + 1) % N;
    signal(mutex); // leave critical section
    signal(full);  // one more filled slot
}
      Consumer
      
while (true) {
    wait(full);    // block if nothing to take
    wait(mutex);
    next_consumed = buffer[out];
    out = (out + 1) % N;
    signal(mutex);
    signal(empty); // one more free slot
    /* consume next_consumed */
}

      Unsynchronized vs. mutually exclusive

      1 · Mutual exclusion

      If a thread is executing in its critical section, no other thread can execute in its own. Here, mutex provides this.

      2 · Progress

      If no thread is in a critical section, one that wants to enter cannot be postponed forever by threads that don't want to enter.

      3 · Bounded waiting

      There is a limit on how many times other threads can enter their critical sections before a waiting thread gets its turn.

      Order matters. If a producer calls wait(mutex) before wait(empty), it can block on a full buffer while still holding the mutex. Then no consumer can enter to free a slot, and the system deadlocks. Always acquire the counting semaphore first.
